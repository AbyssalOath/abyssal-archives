# Storage backends

File bytes are stored through the `StorageBackend` trait
(`src/storage/mod.rs`):

| Method | Purpose |
|---|---|
| `put(key, stream)` | store a byte stream chunk by chunk (browser uploads) |
| `import_from_path(key, path)` | move a local file into storage (incoming-folder imports) |
| `open(key, offset, len)` | read a byte range (downloads, HTTP Range) |
| `delete(key)` | remove an object (missing objects are fine) |
| `size(key)` / `exists(key)` | metadata |

Keys are random UUIDs generated by the app. Each row in `files` records its
`storage_backend` and `storage_key`, so files on different backends can
coexist (e.g. after a migration).

## `local` (default)

`STORAGE_BACKEND=local` stores files under `STORAGE_PATH` as
`<first two key chars>/<key>`. In-progress writes go to `STORAGE_PATH/.tmp/`
and are renamed into place when complete, so a half-written file is never
served. Only well-formed UUID keys are accepted, which rules out path
traversal.

In Docker, `STORAGE_PATH` is `/data/storage`, bind-mounted from
`STORAGE_HOST_PATH` (default `./data/storage`) and owned by UID/GID 10001.

## `smb` (stub)

`STORAGE_BACKEND=smb` selects a compiled stub: the app starts, logs a warning,
and every file operation fails with "not implemented". The variables a real
implementation would use are documented but not read:

`SMB_HOST`, `SMB_SHARE`, `SMB_USERNAME`, `SMB_PASSWORD`, `SMB_DOMAIN`

### Using an SMB share today: mount it on the host

The practical route is to let the host's kernel speak SMB (CIFS) and keep
`STORAGE_BACKEND=local`:

```bash
sudo apt install cifs-utils     # or: dnf install cifs-utils
sudo mkdir -p /mnt/filehost-storage
# /etc/fstab -- uid/gid 10001 = the container user
//nas.example.lan/files  /mnt/filehost-storage  cifs  credentials=/root/.smb-filehost,uid=10001,gid=10001,file_mode=0640,dir_mode=0750,_netdev,nofail  0  0
sudo mount /mnt/filehost-storage
```

`/root/.smb-filehost` (mode 600):

```
username=<user>
password=<password>
domain=<domain>
```

Then point the storage mount at it in `.env` and recreate the app:

```bash
STORAGE_HOST_PATH=/mnt/filehost-storage
docker compose up -d app
```

Notes:

- If the incoming folder is on local disk, imports copy across to the share
  (see docs/IMPORT.md, "Rename vs. copy"). Putting the incoming folder on the
  same share as well makes imports a server-side rename. Use one mount for both.
- Docker's `local` volume driver can also mount CIFS directly
  (`driver_opts: type: cifs`), if you prefer volumes over host mounts.
